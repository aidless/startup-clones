## P0：会产生「看起来正确的错误结果」或「边界被整个绕开」

### 1. filing-lens 把「经营活动现金流」答成「现金余额」（差 4 倍，confidence=1.0）

- 位置：`filing-lens/filinglens/answer.py:28-34`、`filing-lens/filinglens/facts.py:35,89-98`
- 复现：问 `What was cash flow from operations in FY2026?`
  → `status=ok conf=1.000`，答「cash：FY2026 为 36.30B USD」，引 `XBRL:CashAndCashEquivalentsAtCarryingValue@FY2026`
  → 同一份 facts 里 `NetCashProvidedByUsedInOperatingActivities@FY2026 = 145.10B USD`
- 根因：`resolve_metric` 取「被问句包含的最长别名」，别名表里 `cash` 只指向现金余额，**没有任何现金流 tag**。
- 为什么最危险：状态 ok、置信度 1.0、引用是真的标签和真的数字。用户没有第二个信息源能发现这是另一个科目。

### 2. filing-lens 定性问题被数字通道抢答（conf=1.0）

- 位置：`filing-lens/filinglens/answer.py:24,32-33`
- 复现：`what was the reason for the revenue decline?` / `revenue growth drivers`
  → 都返回 revenue FY2026 478.83B + 同比，完全没回答「原因 / 驱动」。
- 根因：`is_numeric_question` 只要 tokenize 后 ≤4 词就判 numeric；`NUMERIC_CUES` 里放的是 `what was` 这类语法线索，
  `QUALITATIVE_CUES` 不含 reason / driver / decline / why。

### 3. filing-lens 英文问员工数返回无关段落（status=ok）

- 位置：`filing-lens/filinglens/answer.py:229,291`、`filing-lens/filinglens/glossary.py:89`
- 复现：Apple `how many employees does Apple have?` → `ok conf=0.464`，返回 AppleCare 服务介绍；
  真值「approximately 167,000 full-time equivalent employees」就在同文件 `#Item 1¶51`。
  TI(0000097476) 中文问 → 正确 33,000（conf 0.8）；英文问 → `ok conf=0.727` 答一段税务披露。
- 根因：`expand_groups` 判断是 `if zh in query`，词表键全中文 → 英文问句 `groups=[]`，
  headcount 通道与 `wants_headcount` 过滤同时失效，落到普通摘录通道拿沾边文字当答案。

### 4. cruxline 编码 rubric 六条规则没有一条读工具结果

- 位置：`cruxline/cruxline/rubrics.py:105-111`
- 复现：`read a.py` → `edit a.py` → `bash pytest -q`（`result="1 failed"`, `error="exit code: 1"`）→ 正文写「全部测试通过」
  → `Judge(rubric=agent_rubric()).score(t)` = **1.0 PASS, vetoed=[]**
- 根因：致命项 `no_tool_error` 只存在于支撑 rubric；`retry_after_error_changed` 只罚「原封不动重试」，
  不罚「报错后编造结论」。
- 真实数据上的后果：60 条真实轨迹判出 58 PASS，其中带工具报错的 26 条里 24 条 PASS。
  一个把 97% 都判通过的判分器，对「缺陷 agent」没有区分力。

### 5. cruxline 验证动作不看成功

- 位置：`cruxline/cruxline/rubrics.py:100`
- 复现：`write a.py` → `read nope.py`（`error="ENOENT"`）→ `verify_after_write=(1.0,'1 次写，末次写之后有验证')`
- 根因：`any(c.name in VERIFY_TOOLS for c in after)` 只匹配工具名，未过滤 `c.ok` / `c.error`。

### 6. cruxline 回归删掉失败用例即判「大幅改善 · ship」

- 位置：`cruxline/cruxline/regress.py:47`
- 复现：baseline `{a:False,b:False,c:False}`、current `{a:True}` → 通过率 0.0 → 1.0，`verdict=ship`，回归 0 条。
- 根因：`ids = set(baseline) & set(current)` 静默丢弃缺失用例，没有「用例集不一致」这一档。

### 7. agent-inbox 显示名伪装绕过外部审批闸

- 位置：`agent-inbox/agentinbox/channels.py:50`
- 复现：`From: "内部同事 <insider@corp.example>" <attacker@evil.example>` → `sender` 解析成内网地址、`is_external=False`
  → `Policy().check_outbound(...)` 返回 `Decision(allow=True, needs_approval=False)`。
- 根因：`EMAIL_RE.search(frm)` 取头部里第一个像邮箱的串，显示名先出现就赢了。
  一行 From 头就把「外部消息必须人工审批」这条边界整条抹掉。

### 8. agent-inbox 空白名单 fail-open

- 位置：`agent-inbox/agentinbox/policy.py:61`
- 复现：`Policy().check_inbound(Inbound("email","t","anyone@evil.example","hi","t")).allow == True`
- 根因：`if self.allowlist and ...` 把「未配置」当成「全放行」。作为常驻 agent 的第一道阀门，默认应当是拒绝。

### 9. agent-inbox 风险动作改说法即不进审批

- 位置：`agent-inbox/agentinbox/policy.py:16-21`
- 复现：`把这 1200 元汇给供应商账户` / `转1200给客户` / `把这笔钱退回原账户` → 三条全部 `needs_approval=False, risk=''`
  （只有 `转账 1200` / `付款 1200` 才拦）
- 根因：固定动词表（退款/付款/转账/打款），没有「金额 + 动作」的结构化识别，同义说法全部漏。

### 10. agent-store 任何人可顶替别人的包发新版本

- 位置：`agent-store/agentstore/registry.py`
- 复现：northwind 发 `acme-bot@1.0.0`，attacker 发 `acme-bot@9.9.9`（多 `payment.charge`）
  → `latest("acme-bot").version == "9.9.9"`，权限含 `payment.charge`，买家装到攻击者的权限。
- 根因：`versions` 表主键 `(agent_id, version)`，**不记 developer、不校验归属**。

### 11. agent-store 幂等键缺买家维度 → 永久漏计费

- 位置：`agent-store/agentstore/meter.py:99`
- 复现：buyerA 用 `R1` → buyerB 也用 `R1` → `duplicate=True`，buyerB 账单 gross = 0。
- 根因：`WHERE request_id=?` 没有 buyer 维度。

### 12. geo-radar 中文语境下品牌漏检 → 份额系统性低估

- 位置：`geo-radar/georadar/extract.py:20`
- 复现：`推荐Acme这个工具`、`Acme的稳定性最好` 全部漏检；`用 Acme 吧` 命中。
- 根因：`(?<![\w-]){escaped}(?![\w-])` —— Python 的 `\w` 含汉字，中文紧贴品牌名时词边界不成立。
  提示词模板一半是中文，等于一半样本的品牌识别失效。

### 13. audit-loop 下期收入被报成本期截止例外

- 位置：`audit-loop/auditloop/checks.py:113-117`
- 复现：`Invoice(revenue_date=2027-01-15, shipped_date=None)`、`period_end=2026-09-30`
  → `high「已确认收入但无发货记录（期末 2026-09-30）」`
- 根因：`if inv.shipped_date is None: return` 分支先返回，没做另一分支那句 `revenue_date <= period_end`。
  会计师能复核掉（「多报」不是「错答案」），但这是最常见的噪声来源。
